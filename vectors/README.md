# Overture test vectors

Each file here is one scenario, generated by `uv run python -m overture.vectors` from fixed salts, nonces and times, so the same code always writes the same bytes (this.i `8kzvymmy`). The test suite regenerates them and fails if any byte differs. Do not edit them by hand; change the scenario in `src/overture/vectors.py` and regenerate.

A file holds:

- `description` and `spec`: what the scenario shows, and the sections of [`docs/spec.md`](../docs/spec.md) it exercises.
- `agent`: the principal's AID, the agent's AID, the agent's URL, and `oobi`, the CESR stream an OOBI of the principal resolves to: the principal's KEL, the agent's KEL, the principal's `/end/role/add` reply naming the agent in the `agent` role, and the agent's `/loc/scheme` reply. Where a scenario needs them, `settings` gives limits the agent runs with (`maxSize`, the largest stream in bytes it parses), and `schemas` lists the credential schemas the agent holds, which it needs to check attached evidence.
- `requester` and `other`: the AIDs of the requester and of a third party whose message the requester passes on. `issuer`, where present, is the AID of a credential issuer whose KEL and TEL events appear in the streams. A scenario may also introduce other requesters, such as a non-transferable or a multi-key one, whose KELs travel in the streams they send.
- `exchanges`: in order, what the requester sends and what the agent must answer.

Each exchange has `agentTime`, the agent's clock when the stream arrives (freshness is judged against it); `send`, the whole CESR stream in text form, which is also the HTTP request body; and `expect`, which is one of:

- `{"status": 200, "answer": ...}`: the exact CESR stream the agent answers with. Agent signatures are Ed25519 and deterministic, so a conforming agent with the same keys and clock produces these bytes. With other keys, compare the answer's parsed messages instead.
- `{"status": 204}`: nothing to send, as after a `seen` receipt.
- `{"status": 204, "refused": {"step": N, "code": ...}}`: a refusal, which is silent on the wire. `step` is the step of the check order in spec §6.1 that refuses the stream; `code` is the reason the reference package logs, which another implementation need not use.
- `{"status": 400, "supportedMajors": [...], "refused": ...}`: an unsupported major version, which the HTTP binding may report as problem details (spec §10).

An exchange may instead have `push`: at `agentTime` the agent runs a pass of delivery on its own initiative (spec §6.9), and `push` lists each `url` it POSTs to with the `body` it sends, empty when it has nothing to push.

To load an agent's key state before replaying a scenario, parse `agent.oobi`. Streams are sent with the agent's clock set to each exchange's `agentTime`, and later exchanges depend on earlier ones, so replay a file from the top.

Together the files cover every refusal reason the reference package has except a change of major version between sends (step 9), which needs an agent supporting two majors; the test suite checks that coverage.
